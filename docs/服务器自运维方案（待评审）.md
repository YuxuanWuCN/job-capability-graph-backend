## 0. 一句话

需求成立（笔记本不常开 → 服务器要能自运维、自更新），但**「自更新」是这台机器上唯一能让全站宕机的动作**，必须用"受控脚本"而不是"agent 自由发挥"来实现。

## 3. 三个方案对比

| 维度 | A 不装（现状） | B 容器化 DSH | C 纯 cron 运维（无 agent） |
| --- | --- | --- | --- |
| 7×24 常驻 | ❌ 依赖人 | ✅ 容器 + restart 策略 | ✅ cron 本来就常驻 |

## 4. 推荐：B + C 组合，按"权限分级"落地

### 4.1 形态

- **容器化运行**，不装宿主机：
  ```
  docker run -d --name dsh --restart unless-stopped \
    --memory 768m --memory-swap 1g \
    -v /opt/job-graph:/work \
    -v /root/dsh-home:/root \
    -v /var/run/docker.sock:/var/run/docker.sock \
    node:24-slim sleep infinity
  ```
- 版本：`@deepseek-ai/dsh`（npm 现值 **0.2.2-rc.5**，要求 **Node ≥ 24.9.0**），国内装用 `registry.npmmirror.com`。
- 常驻任务用**它自己的 schedule** 或系统 cron 调 headless，二选一（推荐 cron，因为可观测、可停）。

### 4.2 权限分级（今晚要定的第一件事）

| 级别 | 挂载 | 能做什么 | 风险 |
| --- | --- | --- | --- |
| L0 只读 | `/opt/job-graph:ro` | 看代码、看日志、诊断 | 无 |
| L1 只读 + docker.sock | 上面 + socket | 重启容器、看容器日志 | 中（可删容器，但代码与数据在卷里） |
| L2 读写 | 去掉 `:ro` | 改代码、拉代码、构建 | **高**（可覆盖源码，已有先例） |

**建议：从 L1 起步，改代码这件事永远走 §4.3 的脚本，不给 agent 直接 `up -d --build` 的权力。**

### 4.3 「自我更新」必须是脚本，不是 agent 的自由动作

生产机上唯一被验证过的安全姿势（已写进交接单 §4）：

```bash
# safe-rebuild.sh —— 放在 /opt/job-graph/deploy/，root:root 755
set -euo pipefail
cd /opt/job-graph
avail=$(free -m | awk '/Mem:/{print $7}')
[ "$avail" -ge 1500 ] || { echo "ABORT: available=${avail}M < 1500M"; exit 1; }
docker compose -f compose.yaml -f deploy/compose.prod.yaml stop api worker scheduler neo4j
docker build -t job-graph-backend:next ./backend
docker tag job-graph-backend:latest job-graph-backend:prev-$(date +%Y%m%d-%H%M%S)
docker tag job-graph-backend:next job-graph-backend:latest
docker compose -f compose.yaml -f deploy/compose.prod.yaml up -d --no-build
for i in $(seq 1 40); do
  code=$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8080/health/ready)
  [ "$code" = "200" ] && { echo "OK"; exit 0; }
  sleep 3
done
echo "FAILED: rolling back"; docker tag job-graph-backend:prev-* job-graph-backend:latest 2>/dev/null || true
docker compose -f compose.yaml -f deploy/compose.prod.yaml up -d --no-build; exit 1
```

**红线（写进制度）**：
1. 禁止在容器全运行时执行 `docker compose up -d --build`（2C4G 会整机卡死，已有两次先例）。
2. 禁止 agent 直接改 `backend/` 源码；
3. 更新只在**凌晨窗口**跑，且必须留 `prev-*` 镜像 + 源码备份；
4. 失败自动回滚，不允许"人工看着办"。

### 4.4 建议的巡检清单（cron，每 5 分钟已有 monitor.sh）

| 频率 | 动作 |
| --- | --- |
| 5 分钟 | `/health/ready`、内存、磁盘、celery 队列（已实现） |
| 每小时 | 备份目录非空且当日有新文件 |
| 每天 03:20 | 全量备份（已实现） |
| 每周日 | 备份恢复演练（对临时库 `pg_restore` 一次） |
| 每月 | 日志轮转检查、镜像清理（`docker image prune`） |

## 5. 今晚需要拍板的三件事

1. **权限给到哪一级？** 建议 L1（只读代码 + 能重启容器），不给源码写权限。
2. **更新窗口定几点？** 建议 03:00–05:00，且必须 trigger 在无人使用时。
3. **失败谁兜底？** 脚本自动回滚 + 微信/短信告警；如果做不到告警，就退回"只巡检不更新"。

## 7. 我的建议（一句话）

**装，但只给它"看和重启"的权限；"自更新"由它来触发、由脚本执行、由回滚兜底。** 这样既解决你笔记本不开机的问题，又不会把线上交给一个没有刹车的执行体。
