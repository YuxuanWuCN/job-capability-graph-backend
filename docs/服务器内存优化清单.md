# 服务器内存诊断与优化清单

> 机器：阿里云 ECS `ecs.e-c1m2.large`（2 vCPU / 3.5 GiB 可用），Ubuntu 22.04，`8.153.183.119`
> 采集时间：2026-11-23 15:30（本次 boot 已连续运行 15 小时）
> 用途：给接手优化的人/agent 一份带实测数据的改造说明。所有数字都是现场 `free` / `docker stats` / `ps` 读出来的，不是估算。

---

## 0. 一句话结论

**现在没有内存泄漏，也没有被 OOM Killer 杀过。** 危险来自结构：**六个容器全都没有内存上限（`mem_limit=0`）**，任何一方（neo4j GC、celery 解析大简历、uvicorn 处理大请求、以及 `docker compose build`）都能把 3.5 GiB 吃干，内核进入直接回收 + swap 抖动，整机表现为「TCP 能握手、应用层不响应」——11-23 00:10 那次假死就是这个形态。

所以优化分两件事：**① 加限额止损**（防止再整机卡死）；**② 降基线**（把常驻从 1.5 GiB 压到 1.0 GiB 左右，给解析任务留出余量）。

## 2. 爆内存的原因（按贡献排序）

### 原因 1｜所有容器都没有内存上限 —— 结构性风险（最致命）

`mem_limit=0`，cgroup 不设边。任何一方超额，压力直接落在宿主机内核上：先回收 page cache，再疯狂换页，最后整机失去响应。**这不是"谁泄漏"，而是"没有边界"。**

### 原因 2｜镜像构建是本机最大瞬时峰值（已实际导致假死）

`docker compose build` 会在本机跑 `uv pip install`（63 个包）+ 前端 `tsc`。首次部署时 pypi 直连只有 18.8 KB/s，构建跑了 21 分钟仍未完成，期间内存被吃满，机器直接假死。**这也是为什么不许在这台机器上随手 `up -d --build`。**

### 原因 3｜neo4j JVM 常驻 585 MB，占常驻总量 46%

heap max 384m + pagecache 256m + JVM 自身（metaspace、线程栈、直接内存）。而图规模极小：当前 **38 节点 / 86 边**，就算扩到 192 个岗位 × ~10 项能力也只有几千节点。**pagecache 256m 对这个数据量是浪费。**

### 原因 4｜Celery 起了 4 个 Python 进程，合计约 562 MB

`beat`（138 MB）+ worker `master`（139 MB）+ 2 个 `child`（143 + 142 MB）。而 `beat` 只做定时投递（每 60 秒重投卡住任务、标记僵尸任务），单独占一个 130+ MB 的 Python 进程性价比极低。

### 原因 5｜Python 进程本身基线高（129 MB/进程）

`import app.main` 就要 129 MB（fastapi + sqlalchemy + redis + neo4j + pypdf + python-docx + celery 全量导入）。于是：api 151 MB、4 个 celery 进程各 ~140 MB —— **光"什么也不干"就已经 700 MB。**

### 原因 6｜简历解析的内存峰值没有护栏

上传上限 `MAX_IMPORT_FILE_BYTES=50MB`，`pypdf`/`python-docx` 解析大文件时峰值可达数百 MB；`-c 2` 两个 child 同时解析就是双份峰值叠加。**平时不显，一到大简历就顶到天花板。**

### 原因 7｜阿里云 agent 约 100 MB，不可控但可计入预算

`AliYunDunMonitor` 44 MB + `AliSecCheck` 44 MB + `AliYunDun` 10 MB。不建议关（安全合规），优化时要把它算进分母。

### 原因 8｜swappiness=20 偏保守，压力上来时先"硬扛"再换页

有 4 GB swap 却几乎不用（6.6 MB）。swappiness 低会让内核优先直接回收 + 卡顿，而不是把冷页挪走。

### 附：不是原因的两个"假象"

- **page cache 1.7 GB**：缓存文件内容，随时可回收，`available` 已把它算进去。
- **neo4j 187% CPU**：`docker stats` 瞬时采样假象；容器内 `top` 显示 java 累计 CPU 时间 14 小时才 `2:07`。

## 3. 改造清单

### 3.1 立刻做（止损，10 分钟）

**A. 给每个容器设内存上限**（`deploy/compose.prod.yaml`，每个 service 加：）

```yaml
    deploy:
      resources:
        limits:
          memory: 1g
```

| 服务 | 建议 limits | 依据 |
| --- | --- | --- |
| neo4j | `1g` | 当前 618 MB，留 GC 余量 |
| worker | `700m` | 当前 246 MB，含解析峰值 |
| api | `450m` | 当前 163 MB |
| scheduler | `200m` | 当前 136 MB |
| postgres | `500m` | 当前 81 MB |
| redis | `200m` | maxmemory 128 MB |

> 好处：超限只杀**这一个容器**（可自动重启），不会拖死整机。
> 注意：`deploy.resources.limits` 需要非 swarm 模式下 `docker compose` v2 支持；若版本较老，用等价的 `mem_limit: 1g` 写法。

**B. 把 swappiness 调高**

```bash
sysctl -w vm.swappiness=60
echo 'vm.swappiness=60' > /etc/sysctl.d/99-swap.conf
```

### 3.2 降基线（约省 480 MB 常驻）

**C. neo4j 降配**（`deploy/compose.prod.yaml`）

```yaml
      NEO4J_server_memory_heap_max__size: 256m
      NEO4J_server_memory_heap_initial__size: 128m
      NEO4J_server_memory_pagecache_size: 160m
      NEO4J_dbms_memory_transaction_total_max: 256m
```

预期：**618 MB → 约 400 MB**（省 ~200 MB）。风险：图很大时 pagecache 命中率下降；当前数据量（几十节点）无影响。

**D. worker 并发降到 1**（解析本来就该串行，2C 机器上并发 2 只会互相拖死）

```yaml
    command: ["celery","-A","app.worker:celery_app","worker","-l","INFO","-c","1","--max-tasks-per-child","20"]
```

预期：**省 1 个 child ≈ 140 MB**；顺带把并发解析峰值砍半。

**E. beat 合并进 worker**（省 1 个进程 ≈ 138 MB）

```yaml
    # 删掉 scheduler 服务，worker 命令加 -B
    command: ["celery","-A","app.worker:celery_app","worker","-B","-l","INFO","-c","1","--max-tasks-per-child","20"]
```

> 权衡：`-B` 在生产环境官方不推荐（beat 与 worker 同生命周期，worker 重启会丢调度）。当前只有"重投卡住任务/标记僵尸任务"这一类定时任务，**可接受**。若坚持独立 beat，就把它 limits 设 200m、进程数不变。

**F. 上传与解析护栏**

- nginx `client_max_body_size` 从 50m 收到 **20m**（与后端 `MAX_IMPORT_FILE_BYTES` 同步改）。
- 解析前检查 PDF 页数（`pypdf` 读页数，> 30 页直接拒绝并提示"简历请控制在 30 页内"）。
- 逐页 `extract_text` 后释放 page 对象，避免整本 DOM 常驻。

### 3.3 流程约束（避免重现）

**G. 禁止在服务器上直接 `docker compose build`**

三种正确姿势，按优先级：

1. 本地构建 → `docker save job-graph-backend:latest | gzip > image.tgz` → `workbench upload` → 服务器 `docker load`；
2. 构建前先 `docker stop worker scheduler neo4j api`，`free -m` 确认 available ≥ 1.5 GB，`build api` 完成后再 `up -d`（已验证可行，本次就是这么过的）；
3. 有条件就上阿里云 ACR，服务器只 `docker pull`。

**H. 监控**（免费且够用）

- 阿里云云监控：给实例配「内存使用率 > 85% 持续 5 分钟」告警，通知到手机。
- 或加一条 cron：`*/5 * * * * free -m >> /var/log/mem.log`，配 logrotate。

## 4. 验收标准（改完怎么证明有效）

1. `docker stats --no-stream` 六个容器合计 **≤ 900 MiB**（当前 1,255 MiB）。
2. `free -m` 的 `available` 在**空载**时 **≥ 2.2 GB**（当前 1.78 GB）。
3. 连续上传 3 份 10 页 PDF 简历，`available` 最低点 **≥ 800 MB**，无容器被 kill。
4. `docker inspect --format '{{.HostConfig.Memory}}'` 每个容器**非 0**。
5. `/health/ready` 返回 `ready`，且 `home=200`。
6. 重启整机后 3 分钟内 6 容器全 Up、`home=200`（验证 `restart: unless-stopped` 已生效）。
