# 同学协作与部署指南

> 目标：同学改完代码 `git push`，负责人点一下按钮，生产服务器就更新。
> 适用仓库：`job-capability-graph-backend`
> 建立日期：2026-11-25

---

## 0. 先说结论：分两层，别混在一起

| 层 | 做什么 | 谁能做 | 风险 |
|---|---|---|---|
| **协作层** | push 分支、提 PR、review、合并 | 全体同学 | 零风险，碰不到服务器 |
| **部署层** | 把合并后的代码送上生产 | 只有负责人点按钮 | 有风险，需审批 |

**同学永远不需要服务器密码、密钥或阿里云账号。** 他们只跟 GitHub 打交道。

---

## 1. 为什么不做「push 就自动上线」

这台机器是 **2 vCPU / 3.5 GiB**，容器常驻 1.6 GB，余量只有 1.7 GB。已经因为部署动作宕过两次：

| 时间 | 原因 | 后果 |
|---|---|---|
| 2026-11-23 00:10 | 容器全运行时 `docker compose up -d --build` | 内存打满，整机 hang，只能控制台重启 |
| 2026-11-24 10:58 | `docker cp` 覆盖容器内代码 | api ImportError，全站 502 约 4 分钟 |

所以流水线的默认触发方式是**手动**（`workflow_dispatch`），并且加了人工审批。

想要「合并即上线」也能开——把 `.github/workflows/deploy.yml` 里 `push: branches: [main]` 那三行取消注释即可。但**务必保留 Required reviewers**，否则任何一次合并都会直接动生产，而学生端可能正在用。

## 2. 同学要做的事（只有这些）

### 2.1 拿到仓库写权限

负责人在 GitHub 仓库 → Settings → Collaborators → Add people，加同学的 GitHub 账号。

> **待确认**：现在本地有两个远端，必须先定哪个是团队主仓库。
> - `origin` → `Showiix/job-capability-graph-backend`（只有 `main`）
> - `fork` → `YuxuanWuCN/job-capability-graph-backend`（有 `main` 和 `feat/paper-empirical-experiments`）
>
> 选定之后，所有人都往那一个仓库提 PR，不要两边各推一份。

### 2.2 日常流程

```bash
git clone <团队主仓库地址>
cd job-capability-graph-backend

git checkout -b feat/你的功能名
# 改代码
git add -A
git commit -m "feat: 一句话说清改了什么"
git push -u origin feat/你的功能名
```

然后在 GitHub 上开 Pull Request，等 review 和合并。

### 2.3 三条纪律

1. **不要直接 push `main`**，走分支 + PR。
2. **不要提交任何凭据**：`.env`、私钥、API key、Cookie。`.gitignore` 已经排除，但别手动 `git add -f`。
3. **不要把 `deploy/` 目录打包发给任何人**。里面有 `_deploy_key`（能登 root 的私钥，虽然被 gitignore，但文件在磁盘上）。

## 3. 负责人要做的一次性配置

### 3.1 生成一把**部署专用**密钥（不要复用现有那把）

为什么不复用：现有私钥同时存在于 `~/.ssh/` 和仓库 `deploy/_deploy_key`，一旦要撤销就得给所有人换钥匙。部署密钥单独一把，泄露了只删它。

在**本机**执行：

```powershell
ssh-keygen -t ed25519 -C "github-actions-deploy" -f "$env:USERPROFILE\.ssh\job_graph_ci_deploy"
```

passphrase **留空**（CI 无法交互输入）。

### 3.2 把公钥加到服务器

把 `job_graph_ci_deploy.pub` 的内容追加到服务器 `/root/.ssh/authorized_keys`：

```bash
cp -a /root/.ssh/authorized_keys /root/authorized_keys.bak-$(date +%Y%m%d-%H%M%S)
printf '%s\n' '<公钥整行>' >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
ssh-keygen -lf /root/.ssh/authorized_keys
```

> 这是写操作，需要负责人确认后执行。回滚就是 `cp` 回备份文件。

### 3.3 配 GitHub Secret

仓库 → Settings → Secrets and variables → Actions → New repository secret

| 名称 | 值 |
|---|---|
| `DEPLOY_SSH_KEY` | `job_graph_ci_deploy` **私钥全文**（含 BEGIN/END 两行） |

**私钥只进 GitHub Secrets，不进仓库、不发群、不写进任何文档。**

### 3.4 建生产环境审批

仓库 → Settings → Environments → New environment → 名字填 `production`

勾选 **Required reviewers**，把自己加进去。

这样每次部署都会在 Actions 页面停住，等你点 Approve 才继续。**这是防误触发的最后一道闸。**

## 4. 怎么部署

1. GitHub → Actions → `deploy-production` → Run workflow
2. 选目标：
   - `both` — 前后端都更新
   - `frontend` — 只改了前端（快，不停服）
   - `backend` — 只改了后端（会短暂停 api/worker/scheduler/neo4j）
3. 点 Run，然后在审批提示处点 Approve
4. 看日志，最后应出现 `result: pass=7 fail=0`

### 流水线做了什么

```
检出代码
  → CI 上构建前端（VITE_API_BASE_URL=http://8.153.183.119:8080）
  → 产物自检（标题含「岗智融析」、viewport-fit=cover、不含 127.0.0.1:8000）
  → 打包 dist.tar.gz / backend.tar.gz
  → SSH 上传（主机公钥已钉死，防中间人）
  → 服务器执行 deploy/ci-deploy.sh
       后端：备份源码 → 解包 → guard.sh safe-rebuild --yes → verify
       前端：guard.sh deploy-dist --yes（自动备份 + nginx 校验 + 首页探测 + 失败回滚）
  → 最终 guard.sh verify
```

**关键约束**：前端在 CI 构建，服务器只做解包和替换。服务器不跑 `npm build`（P0-6）。

## 5. 出问题怎么办

流水线失败时会自动打印 `guard.sh status`、api 日志和回滚点。

`safe-rebuild` 和 `deploy-dist` **本身就带自动回滚**：健康检查不过会退回上一版。所以多数失败不需要人工干预。

需要手动回滚时：

```bash
bash /opt/job-graph/deploy/guard.sh rollback   # 只读，列出所有回滚点
```

然后按它打印的示例执行。**先看清再动。**

## 6. 红线（违反即事故）

| # | 禁止 |
|---|---|
| P0-1 | 容器全运行时 `docker compose up -d --build` |
| P0-2 | `docker cp` 覆盖容器内代码 |
| P0-3 | `.env` / API key / root 密码 / 私钥 进仓库或日志 |
| P0-4 | 改 nginx 的 `listen 8080`、`/api/` 反代、`client_max_body_size 20m` |
| P0-5 | 删 `/opt/backup`、`/root/*-backup-*`、`prev-*` 镜像 |
| P0-6 | 在服务器跑 `npm run build` / `uv sync` |

完整版见 `AGENTS.md` 与 `docs/服务器Agent操作手册.md`。
