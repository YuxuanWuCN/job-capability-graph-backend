# 简历—能力证据标注手册 v1.0

> 归属：岗智融析（跨专业新质岗位匹配系统）
> 版本：v1.0（2026-11-12）
> 状态：**草案，待标注组三人评审后冻结**
> 配套文件：`backend/app/catalog/framework_v1.json`（33 项能力 + 165 条 BARS 锚点）

---

## 0. 这份手册解决什么问题

系统现在能算分，但没有任何人知道分算得对不对。原因不是算法差，是**没有裁判**。

本手册定义这个裁判：给定一份简历，三名标注者各自独立判断「这份简历在哪些能力上留下了什么证据」，然后比对三人结果。三人一致的部分才算真值，不一致的部分走仲裁。

标注集的用途有三个，优先级从高到低：

1. **评测抽取与映射是否正确**（P/R/F1、证据定位准确率）
2. **校准证据强度系数**（现在的 0.40 / 0.70 / 1.00 是拍的）
3. **为后续任何监督式改进提供标签**（没有它，权重只能继续拍）

**本手册不解决**「这个人是否适合这个岗位」——那是效标效度问题，需要企业录用结果，本阶段不做。

## 1. 标注对象

### 1.1 标什么文本

标 **系统解析后的文本**，不是原始 PDF/Word 文件。

获取方式：简历上传完成后调用

```
GET /resumes/{resume_id}/extracted-text
```

返回的 `text` 字段就是标注底本。

**为什么必须用解析后文本**：系统校验证据时用的是 `locate_evidence(redacted_text, quote)`，即 Python 的 `str.find()` 首个匹配位置，返回**字符（码点）索引**。如果标注基于原始文件，PDF 里的换行、分页符、不可见字符会让偏移量全部错位，标注集就无法与系统输出比对。

### 1.2 脱敏规则

解析后文本已做等长替换：

| 类型 | 处理 |
|---|---|
| 手机号 | 替换为等长 `*` |
| 邮箱 | 替换为等长 `*` |
| 身份证 | 替换为等长 `*` |
| 微信号 | 部分遮蔽 |

**等长**意味着偏移量不变。标注时直接在脱敏文本上复制引文即可，不需要还原。

### 1.3 不标什么

- 姓名、联系方式、政治面貌、籍贯、照片
- 自我评价里的形容词堆砌（"认真负责、踏实肯干"）——除非有具体行为支撑，见 §3 规则 R6
- 与 33 项能力无关的内容（兴趣爱好、家庭情况）

## 2. 三个标注任务

每份简历产出三组标签。三者必须一起标，不能分开做，否则会互相污染判断。

### T1｜证据定位（Evidence Span）

判断：这段文本是否构成某项能力的**可核验证据**？

- 是 → 记录 `capability` + `quote`（逐字原文）+ `start` / `end`
- 否 → 不记录

`quote` 必须是底本中**连续出现的原文片段**，一字不差（包括标点、空格）。标完后用 `Ctrl+F` 自查一遍，找不到就是标错。

**长度约束**：`quote` 建议 10–200 字。太短（"Python"）没有语义，太长（整段项目描述）无法定位到具体能力。

### T2｜能力映射（Capability Mapping）

判断：这段证据对应 33 项能力中的哪一项（或哪几项）？

规则见 §3。关键点：

- **一条证据最多映射 3 项能力**，超过 3 项说明这条证据太泛，应拆分成多条
- **允许映射 0 项**——简历里大量内容不构成任何能力证据，这是正常的，不要为了"标满"而硬凑
- 9 项硬技能（gap 轨）与 24 项软能力（translate 轨）**分开标**，不要混在一个标签里

### T3｜证据强度（Evidence Strength）

三档，与代码中的枚举严格一致：

| 值 | 含义 | 判定要点 |
|---|---|---|
| `work` | 在工作/实习岗位中实际使用过 | 有雇主、有职责、有产出。**三者缺一不可** |
| `project` | 在项目/课程设计/竞赛中实际使用过 | 有目标、有本人动作、有结果或交付物 |
| `mention` | 仅提及，无使用行为 | 技能列表、"熟悉""了解"、课程名、工具名罗列 |

**这三档直接决定分数**：`EVIDENCE_FACTORS = {mention: 0.40, project: 0.70, work: 1.00}`。标错一档，同一份简历的匹配分最多差 2.5 倍。这是全手册最容易出错、也最影响结果的地方。

## 3. 判定规则（核心）

以下 R1–R8 是硬规则。**规则冲突时，编号小的优先。**

### R1｜只标原文写了的

不推断、不补全、不"合理想象"。

- ❌ 简历写「参与 ACM 集训队」→ 不能推断「算法能力强」
- ❌ 简历写「统计学专业」→ 不能推断「掌握统计推断」
- ✅ 简历写「用 SPSS 完成 3 组方差分析并撰写结论」→ 可标「统计推断 / project」

### R2｜引文必须逐字可定位

`quote` 在底本中必须能 `find()` 到。改写、概括、拼接都不允许。

### R3｜否定、将来、期望句不算

- ❌「正在学习 Python」
- ❌「计划考取数据分析师证书」
- ❌「虽未使用过 Tableau，但愿意学习」
- ✅「2025.03–2025.08 在 XX 公司用 Python 完成用户行为数据清洗，日均处理 20 万条」

### R4｜课程名不等于能力

课程名只在**同时给出该课程的具体产出**时才可标。

- ❌「主修课程：数据结构、数据库原理、统计学」
- ✅「数据库原理课程设计：设计三范式订单库，编写 40 条 SQL 完成增删改查与索引优化」→ 可标「数据清洗 / project」

### R5｜工具名不等于能力，除非有操作语境

工具/技术名词单独出现，最高只能标 `mention`，且必须映射到该工具对应的能力。

- 「Python、SQL、Excel」→ 数据清洗 / `mention`
- 「用 SQL 完成多表关联，定位到某渠道转化率异常的 3 个环节」→ 数据清洗 / `project`

### R6｜软能力必须有「行为动词 + 对象 + 结果」

软能力是翻译轨的核心，也是最容易被虚词污染的部分。判定公式：

> **做了什么动作 + 对谁/对什么 + 产生了什么可观察结果**

| 写法 | 判定 |
|---|---|
| 「具备良好的团队协作能力」 | ❌ 不标。纯自我评价 |
| 「负责社团 30 人招新，协调 4 个部门排期」 | ✅ 团队协作 / `project` |
| 「与产品、设计、开发三方对接，推动需求按期上线」 | ✅ 跨部门沟通 / `work` |
| 「抗压能力强」 | ❌ 不标 |
| 「在 3 周内同时推进 2 个项目，按期交付」 | ✅ 抗压韧性 / `project`（需结合上下文判断是否在岗） |

### R7｜一条证据最多 3 项能力

跨专业迁移的价值恰恰体现在「一段经历同时支撑多项能力」。但超过 3 项就失去区分度，应拆分。

示例（可标 2 项）：

> 「独立完成校级调研项目：设计 200 份问卷、用 Excel 清洗数据、撰写 8000 字报告并在学院答辩获一等奖」

- 数据清洗 / `project`
- 写作能力 / `project`
- （若报告中有明确的论证结构描述，可再加「逻辑思维」）

### R8｜硬技能标「缺口」，软能力标「迁移」

- 9 项硬技能（数据清洗、统计推断、数据可视化、文本挖掘、提示工程、AI 内容生成、图文编辑、短视频制作、交互内容制作）→ **只关心有没有，不关心多强**。没标到就是缺口，这是设计意图。
- 24 项软能力 → **关心证据强度**，因为这是跨专业候选人的主要资产。

## 4. 边界案例（先看这十个再开标）

这十类写法在真实简历里出现频率最高，也是最容易分歧的地方。**标注前必须逐条讨论并达成一致。**

| # | 原文写法 | 正确判定 | 理由 |
|---|---|---|---|
| 1 | 「熟练使用 Office 办公软件」 | 不标（或数据清洗 / `mention` 上限） | 无操作对象，无产出 |
| 2 | 「获校级一等奖学金」 | 不标能力，记入教育背景 | 奖项不等于能力证据 |
| 3 | 「担任班长，负责班级日常事务」 | 团队协作 / `project`（弱） | 有角色有职责，但无具体结果，强度偏低 |
| 4 | 「参与国家级大创项目（成员）」 | 需看下文是否有本人动作，否则不标 | 仅仅"参与"不构成证据 |
| 5 | 「自学 Python 三个月」 | 数据清洗 / `mention` | 有学习行为，无使用产出 |
| 6 | 「用 ChatGPT 辅助写论文」 | AI 内容生成 / `project`；提示工程 / `mention` | 有使用，但无提示设计证据 |
| 7 | 「英语六级 580 分」 | 不标 33 项能力 | 语言能力不在框架内，记入基础信息 |
| 8 | 「负责公众号运营，粉丝从 0 到 5000」 | 写作能力 / `work`；数据可视化视是否有数据复盘而定 | 有明确产出指标 |
| 9 | 「跨专业选修心理学课程并完成课程论文」 | 跨界迁移 / `project`；写作能力 / `project` | 跨专业学习行为本身就是迁移证据 |
| 10 | 「熟悉机器学习常见算法」 | 不标（无对应能力项） | 框架无「机器学习」项，不得强行映射到「数学建模」 |

**第 10 条尤其重要**：33 项能力是封闭集合，超出集合的内容一律不标，不允许"就近映射"。

## 5. 工作流程

### 5.1 阶段一：试标（第 1–2 周）

| 步骤 | 内容 | 产出 |
|---|---|---|
| 1 | 三人各自读本手册 | — |
| 2 | 各标 5 份简历（同一批，互相不看） | 15 条标注记录 |
| 3 | 开会对齐分歧，逐条记录裁决理由 | 《分歧裁决记录》 |
| 4 | 修订手册 → v1.1 | 冻结版手册 |

**这一步不能省。** 直接开标 40 份，标到一半发现规则理解不一致，前面全部作废。

### 5.2 阶段二：正式标注（第 2–3 月）

- 40 份简历（建议 30 份正式 + 10 份备用）
- **双人独立标注 + 第三人仲裁**
- 标注者之间在标注期间不得讨论具体样本
- 每份简历记录：标注者、标注时间、耗时

### 5.3 阶段三：仲裁（与标注同步）

第三人只看分歧点，不看前两人的完整结果，避免被锚定。

仲裁需记录：

- 分歧的具体字段
- 采纳哪一方 / 第三种方案
- 理由（对应本手册哪条规则）
- 若规则未覆盖 → 记为「规则缺口」，进入手册 v1.2

### 5.4 工作量估算

按每份简历 15–25 条证据、每条 1–2 分钟计：

- 单份标注：30–50 分钟
- 40 份 × 2 人 = 80 人次 ≈ **50–65 小时**
- 仲裁：约 15 小时

**三个人分摊，两周可完成主标，一个月含仲裁可全部结束。**

## 6. 验收指标

### 6.1 一致性门槛

| 指标 | 计算方式 | 门槛 | 说明 |
|---|---|---|---|
| 能力映射一致性 | Cohen's κ（两人） | **≥ 0.70** | 0.61–0.80 为"较强一致"，>0.80 为"几乎完全一致" |
| 证据强度一致性 | Cohen's κ（两人） | **≥ 0.60** | 三档判定本身比二分类更难 |
| 证据片段重合度 | 字符级 F1（span 级） | **≥ 0.85** | 允许边界小幅偏移 |
| 整体标注一致性 | Fleiss' κ（三人） | **≥ 0.65** | 含仲裁前原始结果 |

**门槛未达标时的处理**：不降低门槛，回到 §5.1 重做规则对齐。门槛本身可以在 v1.1 中调整，但必须在看到正式标注结果**之前**定下来——否则就是事后凑数。

### 6.2 系统评测指标

标注集完成后，用它对系统打分：

| 任务 | 指标 | 说明 |
|---|---|---|
| T1 证据定位 | Precision / Recall / F1（span 级） | 系统给出的 quote 是否落在人工标定的 span 内 |
| T1 严格版 | Exact Match | start/end 完全一致的比例，作为下界 |
| T2 能力映射 | Micro-F1 / Macro-F1 | 33 类不均衡，必须同时报 Macro |
| T3 强度分级 | 混淆矩阵 + 加权 κ | 重点看 `work` 被误判为 `mention` 的比例 |
| 端到端 | 匹配等级一致率 | 系统等级 vs 人工判定的「是否值得推荐」 |

### 6.3 必须同时报告的基线

没有基线的数字没有意义。至少三条：

1. **关键词基线**：用 209 个别名直接字符串匹配
2. **纯 LLM 基线**：让模型直接输出能力列表与分数，不做证据定位
3. **本系统**

## 7. 交付格式

每份简历一个 JSONL 文件，每行一条证据：

```json
{
  "resume_id": "uuid",
  "annotator": "A",
  "text_sha256": "解析后文本的哈希，用于确认底本一致",
  "capability": "数据清洗",
  "track": "gap",
  "quote": "原文逐字片段",
  "start": 128,
  "end": 156,
  "strength": "project",
  "section": "project",
  "note": "可选，标注者的判断说明"
}
```

字段约束：

- `capability` 必须与 `framework_v1.json` 中的 `name` 完全一致（含空格，如「AI 内容生成」）
- `track` 取 `gap` / `translate`，与框架一致
- `section` 取 `education` / `experience` / `project` / `skill` / `other`
- `start` / `end` 为 Python 字符索引，`text[start:end] == quote` 必须成立
- `annotator` 用代号（A/B/C），不写真实姓名

**校验脚本必须能自动拒绝**：`quote` 找不到、`capability` 不在框架内、`track` 与框架不符、`start/end` 与 quote 不匹配。

### A.2 BARS 五级行为锚点

> 标注时用它对证据「深度」做参照。注意：T3 只有三档，BARS 是辅助判断，不是第四档输出。

| 企业提供 | 0–10 份 | 如有，优先纳入 |

### 9.2 分层要求

必须覆盖以下维度，否则结论不可外推：

- **专业**：理工 / 经管 / 人文 / 艺术，各不少于 6 份
- **学历**：本科不少于 30 份，专科/硕士各 3–5 份
- **经历**：有实习 ≥ 50%
- **目标岗位族**：J1–J4 各不少于 8 份（允许一人多族）

### 9.3 伦理与合规

- 每份简历需**书面授权**（微信文字确认可，需截图留档）
- 存储时移除姓名、电话、邮箱、身份证、照片
- 标注文件仅存于本地，不上传任何第三方服务
- 项目结项后 6 个月内销毁原始文件，只保留标注结果

## 11. 尚未决定、需要三人开会拍板的事项

以下五条本手册**没有**给出答案，因为它们是团队决策，不是技术问题：

1. **一份简历标多少条算合格？** 建议不设上限，但需统计分布，异常少（<5 条）或异常多（>40 条）的样本要复核。
2. **`mention` 是否全部标注？** 若全标，工作量翻倍且信息量低；建议只标与目标岗位族相关的 `mention`。
3. **同一段文字能否既是 `work` 又是 `project`？** 建议取高不取低，只标一次。
4. **仲裁者是否需要具备领域背景？** 建议至少一人有 HR 或招聘实习经历。
5. **标注者是否能看到系统输出？** **绝对不可以**。看到就会被锚定，一致性指标立刻失真。
