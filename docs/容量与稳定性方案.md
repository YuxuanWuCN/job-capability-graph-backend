# 容量与稳定性方案（5000 人 / 一个月）

> 结论先行：**「5000 人一个月」在总量上是安全的，真正的风险不在总量，集中在三个点**——
> ① 集中时段的并发打开、② 简历解析队列、③ 单点无冗余 + 明文 HTTP。
> 本文所有数字来自 2026-11-23 对生产机（阿里云 ECS 2C4G / 上海）的真实压测与系统读数，不是估算。

---

## 一、结论

| 维度 | 现状 | 对 5000 人/月的判断 |
| --- | --- | --- |
| 接口吞吐 | 外部 50 并发实测 **86.8 RPS**、0 错误 | 余量约 30~40 倍（见 §三推算） |
| 首屏体积 | **318 KB**（gzip JS/CSS 207 KB + 主视觉 111 KB） | 5000 人 × 1.5 MB ≈ 7.5 GB/月，流量费约 6 元 |
| 简历解析 | 2 并发 × 9 秒 ≈ **800 份/小时** | 一个月 5000 份没问题；**500 人同时上传要排队 37 分钟** |
| 内存 | 2 workers 稳态可用 **1.6~2.2 GB** | 够用，但 4 GB 机器没有余量做「同时构建镜像」 |
| 磁盘 | 20%（59 GB 用 12 GB） | 5000 份简历约 1.5 GB，够 |
| 可用性 | 单节点 + `unless-stopped` + 看门狗 | **无法承诺 99.9%**，只能承诺「挂了 5 分钟内自愈」 |

一句话：**能跑，但「稳定」要靠三个非功能项兜底**——监控日志、备份可恢复、并发错峰。

## 二、实测数据

### 2.1 优化前（1 个 uvicorn 进程、无图谱缓存）

外部 50 并发 30 秒：

```
并发=50  成功=1305  失败=0  总 RPS=41.8  错误率=0.00%
图谱      p50 1210ms  p95 1604ms  p99 2156ms
岗位列表  p50 1058ms  p95 1507ms  p99 2140ms
```

### 2.2 优化后（2 个 uvicorn 进程 + 图谱 5 秒缓存 + nginx 上游长连接）

外部 50 并发 30 秒：

```
并发=50  成功=2645  失败=0  总 RPS=86.8  错误率=0.00%
图谱      p50 411ms  p95 1388ms  p99 2207ms
岗位列表  p50 437ms  p95 1344ms  p99 1905ms
```

服务器内 100 并发 20 秒（压测器和被测服务抢同一颗 2 核 CPU，属下限）：

```
并发=100  成功=1704  失败=0  总 RPS=79.9
图谱      p50 896ms  p95 3149ms
```

**读法**：RPS 从 41.8 → 86.8（约 2.1 倍），p50 从 1210 ms → 411 ms（约 3 倍提升）。
100 并发时 p95 抬到 3 秒，说明这台 2 核机器在「百级并发」才开始吃力，正好覆盖「一个班/一个会场同时打开」的量级。

### 2.3 服务端自身耗时（排除网络）

- 首页 ttfb：**0.45 ms**（nginx 直出静态文件）
- `/api/v1/graph` 回环：**40~90 ms**，命中缓存后约 **5 ms**
- Neo4j `PROFILE MATCH (d:Domain)`：**138 µs**；图规模仅 38 节点

→ 服务端不是慢在数据库，慢在「同一份图谱被每个人重算一遍」。缓存是这次最划算的改动。

## 三、5000 人/月 的容量推算

单次学生完整流程（游客进入 → 上传 → 确认画像 → 看推荐 → 看成长路径）约 **25~35 次接口调用**。

```
5000 人 × 30 次 = 150,000 次请求/月
150,000 ÷ 86.8 RPS ≈ 29 分钟（纯满速）
```

即使全部集中在 3 天内完成、每天 8 小时，平均也只有 **1.7 RPS**——是实测能力的 **2%**。
所以**总量维度不存在风险**，风险全部来自「同一分钟内的并发峰值」。

### 峰值场景推演

| 场景 | 瞬时请求 | 消化时间 | 学生体感 |
| --- | --- | --- | --- |
| 100 人同时打开图谱页 | ~400（每人 4 个接口） | ~5 秒 | 1~2 秒出图，可用 |
| 300 人同时打开 | ~1200 | ~14 秒 | 部分人 3~5 秒，可忍受 |
| 500 人同时上传简历 | 500 个解析任务 | **37 分钟排队** | 会以为系统坏了 ← **最大风险** |
| 5000 人分散在一个月 | — | — | 无感 |

## 四、已做的改动（2026-11-23）

| # | 改动 | 位置 | 效果 |
| --- | --- | --- | --- |
| 1 | uvicorn `--workers 1` → `2` | `deploy/compose.prod.yaml` | 吞吐翻倍，内存 +约 140 MB |
| 2 | Celery `-c 1` → `-c 2`，上限 1 GB | 同上 | 解析 400 → 800 份/小时 |
| 3 | Postgres `max_connections` 50 → 150，`shared_buffers` 192 MB | 同上 | 2 workers × 池 15 + celery 子进程不再抢连接 |
| 4 | nginx 上游 `keepalive 64` + 清空 `Connection` 头 | `deploy/nginx.conf` | 高并发下不再每个请求新建 TCP |
| 5 | 静态资源与图片关访问日志、图片缓存 30 天 | 同上 | 减少磁盘 IO 与日志量 |
| 6 | **图谱读接口 5 秒内存缓存**（发布即失效） | `backend/app/graph/cache.py` + `router.py` + `service.py` | p50 1210 → 411 ms，重复查询归零 |
| 7 | 看门狗 cron（每 5 分钟） | `deploy/monitor.sh` | 站点不可用自动重启 api；内存/磁盘/队列积压留痕 |

当前容器内存限额：postgres 600m / redis 200m / neo4j 1g / api 700m / worker 1g / scheduler 200m。

## 五、还没解决的三件事（必须知道）

### 5.1 解析队列是硬瓶颈

- 单份简历解析约 **9 秒**（主要等 DeepSeek），2 并发 → **800 份/小时**。
- 若组织方在宣讲会现场让 500 人同时上传，第 500 个人要等 **37 分钟**。
- **对策（任一）**：
  1. 按班级/学号分批通知，每批 ≤100 人，间隔 15 分钟；
  2. 页面上明确「已提交，正在解析，通常 1 分钟内完成」，不要让人反复刷新重传；
  3. 若要真正扛住 500 人同时上传，需要把 worker 提到 4~8 并发 → 换 8 GB 机器（当前 4 GB 会在解析峰值 OOM）。

### 5.2 明文 HTTP + 简历个人信息

- 现在是 `http://8.153.183.119:8080`，简历里通常有手机号、邮箱、学校、经历。
- 学生用校园网/4G 传输，链路上可被同网段嗅探；cookie 也是明文。
- **对策**：备案域名 + HTTPS（约 1~2 周，来不及就用下面的降级方案）；或把服务迁到香港/海外节点（免备案，可立即上 HTTPS，但大陆访问延迟 40~80 ms）。
- 在拿到 HTTPS 前，至少做到：不收集身份证号；宣讲时说明「演示数据请勿填写真实证件信息」。

### 5.3 单点，没有冗余

- 一台 ECS、一个 Postgres、一个 Neo4j。机器挂了就是全站不可用，只能从控制台重启。
- 已有：容器 `unless-stopped`、看门狗 5 分钟内拉起 api、每日备份。
- **不能承诺**「一个月零中断」；能承诺的是「挂了能自愈 / 数据能恢复」。
- 数据中心级故障无法兜底，这是单机方案的固有上限。

## 六、一个月运行的运维清单

### 每天（1 分钟）

```bash
ssh root@8.153.183.119 'tail -20 /var/log/job-graph-monitor.log'
```

看三件事：`ready=200`、`avail` 是否持续低于 300M、`queue` 是否长期大于 0。

### 每周

```bash
# 备份是否真的在产生
ls -lh /opt/backup | tail -3
# 容器是否都在跑
docker compose -f /opt/job-graph/compose.yaml -f /opt/job-graph/deploy/compose.prod.yaml ps
```

### 每月（或上线前一次）

**备份恢复演练**（当前备份已验证能生成，但没验证过能恢复）：

```bash
# 1. 造一个临时库
docker exec job-graph-postgres-1 createdb -U job_graph restore_test
# 2. 灌入最近的备份
gunzip -c /opt/backup/<最新>/postgres.sql.gz | docker exec -i job-graph-postgres-1 psql -U job_graph -d restore_test >/dev/null
# 3. 核对关键表行数（应与生产一致）
docker exec job-graph-postgres-1 psql -U job_graph -d restore_test -tAc \
  "select (select count(*) from users), (select count(*) from job_roles), (select count(*) from resumes);"
# 4. 删掉临时库
docker exec job-graph-postgres-1 dropdb -U job_graph restore_test
```

### 出问题时的第一反应

| 现象 | 先查 | 处理 |
| --- | --- | --- |
| 打不开网页 | `tail /var/log/job-graph-monitor.log` | 看门狗已自动重启 api；仍 502 就 `docker compose ... up -d --no-build` |
| 上传后一直「处理中」 | `docker logs job-graph-worker-1 --tail 50` | 多为 DeepSeek 超时；任务会自动重试，队列积压时 `-c` 提到 3 |
| 整机无响应（SSH 都卡） | 阿里云控制台 | 只能重启实例；重启后 2~3 分钟自动恢复（预热脚本会主动热一次图谱） |
| 页面极慢 | `docker stats` | 若 api 打满 700m，说明并发超预期，临时 `--workers 2` → 3 |

## 七、如果要「更稳一点」，下一步按性价比排序

1. **换 8 GB 机器**（约 +100~150 元/月）：worker 可到 4 并发，解析队列风险直接减半，构建镜像也不再需要停机。**性价比最高**。
2. **备案域名 + HTTPS**：解决个人信息明文传输，同时让扫码/宣传更体面。
3. **接入阿里云云监控告警**（短信/邮件）：当前看门狗只写日志，没人看等于没有告警。
4. **对象存储放简历文件**（OSS）：把 `/data/files` 从系统盘迁走，为磁盘扩容和备份提速。
5. **静态资源上 CDN**：首屏 318 KB 已经很小，收益有限，优先级最低。

## 八、回滚方式

任何一项改动都能单独回滚：

```bash
cd /opt/job-graph
# 配置回滚（每次改动都在 /root 下留了带时间戳的备份）
cp /root/compose.prod.yaml.bak.<ts> deploy/compose.prod.yaml
docker compose -f compose.yaml -f deploy/compose.prod.yaml up -d --no-build
# 前端回滚
cp -r /root/dist-backup-<ts>/. /var/www/job-graph/dist/
# 代码回滚（graph 缓存）
cp /root/graph-backup-<ts>/*.py backend/app/graph/ && 重新 build
```

> 注：这台 2C4G 机器上**不要在业务高峰构建镜像**。安全姿势：确认 `free -h` 可用 ≥1.5 GB → `stop api worker` → `build api` → `up -d`（本次即按此执行，停机约 40 秒）。
